# MAXIMUS dedicated game-server node

This is the outbound Linux agent for `/server-rentals`. It manages reviewed, operator-supplied, digest-pinned game-server containers through rootless Podman. It is separate from the interactive streaming agent in `host-agent/`. No game image, publisher licence, hardware or public game port is supplied by this repository. The example configuration is a non-operational placeholder, not a working CS2 distribution.

The portal implements review, free reservations of 30–240 minutes, scheduled starts up to 24 hours ahead, fixed resources and ports, controls, private logs, team access and up to three local backups. Resources are held from booking until a matching cleanup receipt, including the time before a scheduled start. Stopping keeps the reservation; release or expiry deletes game data and backups. Local backups do not protect against loss of the node. Paid rental billing is disabled.

## Prepare the actual node

Use a dedicated, unprivileged Linux account, Python 3.11+, Podman with cgroup v2 CPU/memory/pids delegation, subordinate UID/GID ranges, `slirp4netns`, and adequate CPU and RAM. Install and review the licensed image yourself; the agent never pulls an image, runs a host shell, executes a member-supplied command or accepts a member-supplied filesystem path.

Configure Podman's `volume_path` and the agent `dataDir` on the **same dedicated, size-bounded filesystem**, owned by the service account. Its total filesystem capacity must not exceed the node's registered `storageMb`. A directory on an unrestricted larger filesystem fails preflight. Keep image layers/Podman graph storage on a separately bounded operator-managed filesystem. Set `dataDir` mode to `0700`. The agent creates named volumes on the bounded data filesystem and checks their device at preflight.

Each booking reserves five times the template's data budget: active data, three backups and one restore staging volume. CPU, RAM, pids, writable temporary filesystems and container log size have container limits. Per-lease game-data usage is **monitored**, not enforced by a per-volume filesystem quota; excess data stops that lease. The bounded data filesystem is the aggregate hard cap. A game can temporarily consume shared free space before the next check, so additional independently configured per-volume quotas or separate nodes are needed where tenant-level disk availability is required. Do not describe the monitored limit as a hard per-lease quota.

The operator must configure host/network firewall policy: expose only the registered game ports, prevent workload access to host services, private management networks and cloud metadata, and permit only game traffic that the licensed build requires. The agent's outbound management API needs HTTPS access to the portal; no inbound management port is needed. `allow_host_loopback=false` alone is not a complete egress firewall. Review container/kernel isolation and the publisher's multiplayer/anti-cheat requirements on the actual machine.

## Enrol and run

1. Register the real node on `/server-rentals` with its resource budget, region, game hostname and a port range of at most 512 ports. Copy the returned node ID into a private copy of `config.example.json`.
2. Replace every placeholder with the installed, licensed image's qualified digest, exact startup argument vector, immutable game template key and resource limits. The process runs as UID/GID 1000 with `/data` as its writable game directory. Games needing host networking, root, privileged containers, host sockets or a writable root filesystem are unsupported. Prepare a compatible image rather than loosening the isolation flags.
3. Keep non-secret settings in `env`. For game secrets use `secretEnv`, for example `{"SERVER_PASSWORD":"MV_GAME_SERVER_PASSWORD"}`, and supply that `MV_GAME_` variable in the service environment. The node credential cannot be mapped into a game. The temporary environment file is private and removed after container creation. Like other local administrators, the operator can inspect game process environment; local service-account access is trusted.
4. Run `python3 agent.py --config /absolute/private/config.json --describe`. Copy its name, game, key, fingerprint, resource limits and ports to the portal template form; attach an HTTPS evidence reference for the build and game rights. This output does not contain game secrets. A different manifest needs a new template key and independent review. The same operator cannot approve their own node or template.
5. During a maintenance window, run `python3 agent.py --config /absolute/private/config.json --preflight`. It first stops this node's managed containers. An unavailable image or required game secret is excluded from ready templates. Failed rootless/cgroup/storage/capacity checks prevent startup. Review each supported game's startup, connection, shutdown, expiry and restore on this actual host.
6. Create a node key in the portal. Store it only as `MV_RENTAL_NODE_KEY` in the service account's private environment file (`0600`); never put it in a URL, config committed to git or shared log. The portal shows it once and stores only its hash. Rotating/revoking it disables new reservations and releases existing bookings. After rotation, install the new key so the agent can acknowledge cleanup, then re-enable reservations in the portal.
7. Install the supplied systemd **user** service with the code at `%h/maximus-server-agent` and private config/environment at `%h/.config/maximus-server/`. Enable the user service and its required user-session persistence through the host administrator. `ExecStopPost` stops node-labelled containers when the service exits. The agent also holds a state lock to reject a second process using its data directory. Do not run multiple agents for one node in different directories.
8. After independent node/template approval, enable new reservations. Only a fresh heartbeat with a matching locally available fingerprint makes an offer visible; capacity and ports are rechecked transactionally at booking.

## Failure behaviour

The agent polls every five seconds. It validates the HTTPS origin, rejects redirects, bounds request/response sizes, validates the node identity/capacity and requires clocks within 30 seconds before renewing contact. Server keys only authorize that node's telemetry and plans. Children receive a filtered environment without node keys or game secrets.

A separate watchdog process kills node-labelled containers after 40 seconds without validated contact, checked every two seconds; the local stop command has a 20-second timeout. The regular loop also stops containers on failed requests. This watchdog covers a stalled control operation or long backup. The systemd stop hook covers service termination. Podman's independent container timeout enforces the booking end even if the agent is killed. These controls require a healthy host/kernel and working container runtime; hardware failures cannot be acknowledged remotely.

The portal releases capacity only after the current command revision is reported stopped **and cleaned**. A network outage, old revision, revoked credential, or expired reservation never frees capacity speculatively. A new key can finish cleanup of old reservations. Until then their resources remain held. The agent cleans local expired state while disconnected; it sends the authoritative receipt on reconnect. If a game exits unexpectedly, an explicit restart is required after inspecting the private log. Node/template suspension and account deletion release affected reservations.

Backups run only after the node confirms the current stopped revision. Archive files are bounded and checked before use: regular files/directories only, no traversal, absolute paths, links, devices, sparse files or privileged mode bits. Restore validates the original digest, imports into a separate named volume, persists the volume switch and completion receipt, then removes the old volume. A failed import keeps the previous active volume. Job receipts survive agent restart and make retries idempotent. Cancellation/release prevents the portal from accepting stale job results. All local copies disappear on final cleanup.

## Verification

`python3 -m unittest discover -s server-agent -v` exercises plan rejection, command revisions, scheduled/expired leases, bounded logs, secret isolation, backup replay, staged restore and failure preservation against an isolated container adapter. Portal domain tests use an isolated embedded database; `RENTAL_PG_TEST_URL` enables real concurrent PostgreSQL checks and must point to a local database named `c25_*`. Browser acceptance covers the member, operator and reviewer surfaces and the actual local HTTP agent protocol.

Container argument checks and an adapter are **not** acceptance of a real game image, rootless runtime, public network, disk setup or publisher licence. Do not advertise a live game node until those external checks are recorded by its independent reviewer.
