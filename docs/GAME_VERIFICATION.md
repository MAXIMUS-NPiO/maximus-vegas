# Game verification preparation — NOT live-verified

C-37 adds a server-side PUBG adapter and a shared pending-score receipt pipeline. No publisher key, live player result or ownership proof is created by this change. Mock HTTP responses exist only in tests. Neither a receipt nor a configured key automatically approves a score.

## Configuration and protocol

Set `PUBG_API_KEY` privately on the server, `PUBG_SHARD` to the approved platform (`steam`, `kakao`, `psn`, `xbox`, `console`), and `PUBG_MATCH_MODE` explicitly to `normal` or `custom`. Optional `PUBG_GAME_MODE` restricts the exact publisher mode; `PUBG_REQUESTS_PER_MINUTE` can lower the conservative application cap of 10. Missing/invalid configuration fails closed. Do not expose a `NEXT_PUBLIC_` key or paste credentials into chat.

`PubgAdapter.account(accountId)` fetches a publisher account record. `match(matchId, accountId)` fetches `https://api.pubg.com/shards/{shard}/matches/{id}` with server-held authorization, validates canonical UUID/account/shard/participant/mode, bounds decoded response size to 2 MB, uses a five-second timeout and refuses redirects. Persistent transactional request budgets cover errors and new process instances; 429 Retry-After/reset cooldowns persist. Authentication, unavailable/expired match, malformed response and rate-limit failures have distinct safe error codes. No automatic retry storm is implemented.

The adapter preserves exact numeric kills, assists, headshots, damage, total movement distance and placement. It does **not** derive deaths from `deathType`, invent missing fields, round stats into the tournament contract, or equate the publisher's `createdAt` (API storage time) with actual match start. Receipt fields are `reportedAt` and `durationSeconds`. A complete event-window verification needs a trusted actual play timestamp (for PUBG, validated telemetry) and approved mode-specific death/recall, precision and team rules. Until those are approved and implemented, score review remains manual. Receipt data is evidence for a review, not proof that all scoring fields are verified.

Primary specifications reviewed: [PUBG match schema](https://github.com/pubg/api-documentation-content/blob/master/swagger/en/schemas/match.yml), [participant schema](https://github.com/pubg/api-documentation-content/blob/master/swagger/en/schemas/participant.yml), [rate limits](https://documentation.pubg.com/en/rate-limits.html), [request platforms](https://documentation.pubg.com/en/making-requests.html). The application conservatively budgets match calls even though the publisher documents a separate match/telemetry quota treatment.

## Binding and the shared pipeline

`verifyPendingScore(db, entryId, revision, rosterMemberId, options)` is an internal service/job entry point, not a public receipt-submission endpoint. It requires the saved pending revision, a registered solo roster member and a stored ownership binding before calling a provider. Team scoring refuses with `team_rules_required`. A correction during the external request causes `stale_submission`; the older result cannot overwrite the new revision. Receipts deduplicate by game + external account + canonical match, including across portal users/events. The match must equal the saved score reference. Receipt persistence never changes the review status.

PUBG's `game_account_bindings` starts empty; no player form, API lookup or Steam display-name match can populate a verified binding. The owner must choose and approve the proof procedure. Only then should an authenticated, audited operator binding flow be implemented; do not populate it with guessed ownership.

CS2 reuses `player_experience_identities`, populated by the existing Steam OpenID verification. A Steam ID proves that binding, not ownership of an arbitrary CS2 score. `Cs2ResultAuthority` is the explicit server-side interface for the chosen managed-server/demo/FACEIT authority. With no trusted implementation, `cs2Receipt` returns `authority_not_configured`. FACEIT history/Steam summaries are not silently promoted into authoritative tournament results. Browser data must never be passed as a trusted adapter.

Acceptance: configure the real key in staging; bind an owner-controlled account with approved evidence; ingest a real match; compare publisher stats, shard/mode and actual time evidence; retry the same match and require one receipt; submit it under another account and require refusal; correct the saved revision during a delayed fetch and require stale rejection. Exercise 401, 404, 429, timeout and malformed/oversized responses. Scores must still remain pending. Record the source commit, real match IDs privately, reviewer and timestamp. Only that evidence can change the NOT live-verified status.
